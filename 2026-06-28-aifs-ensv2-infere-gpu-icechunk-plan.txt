  Short answer

  Yes. anemoi-inference 0.8.3 already ships a native ZarrOutput, and Icechunk
  exposes a Zarr-v3 store backed directly by GCS. So the model can write
  straight into a transactional Icechunk store on GCS during inference — no
  local GRIB staging, no separate upload step. I just proved the core loop
  end-to-end: created a GCS-backed Icechunk repo with your coiled-data.json,
  wrote a (member, time, values) ensemble with one commit per member, and read
  it back with xarray. (Then cleaned up the POC objects.)

  (Installed icechunk==2.0.6 + zarr==3.2.1 into the v2 venv for the test; 
  xarray/cfgrib were already there.)

  How it plugs in — two paths

  Path A — write Icechunk directly during inference (what you described, 
  recommended).
  Replace the GribFileOutput block in
  fp16_multi_run_AIFS_ENS_v2.run_ensemble_member with a Zarr/Icechunk writer.
  Per-member loop becomes:

  import icechunk, zarr
  storage = icechunk.gcs_storage(bucket="aifs-aiquest-us-20251127",
                                 prefix="20260625_0000/icechunk_v2",
                                 service_account_file="coiled-data.json")
  repo = icechunk.Repository.open_or_create(storage)   # once, before the member
  loop
  # (init the (member,time,values) schema once, commit)

  # per member:
  session = repo.writable_session("main")
  root = zarr.open_group(session.store, mode="r+")
  for state in runner.run(input_state=input_state, lead_time=LEAD_TIME):
      for name, val in state["fields"].items():
          root[name][member_idx, step_idx, :] = val      # region write
  session.commit(f"member {member:03d} / 20260625")       # straight to GCS, 
  ACID

  That deletes the entire download-pkl → infer → write 21 GB GRIB → upload → 
  cleanup churn and the /scratch staging. A crashed member just leaves the last
  good commit; you re-run that one member.

  Path B — keep GRIB, convert afterward. Post-process each member's GRIB via
  cfgrib→xarray→to_zarr(session.store). Keeps Steps 3–5 working off GRIB during
  a transition, but doubles I/O (write GRIB, read it back, write Zarr). Good as
  a migration bridge, not the end state.

  What data / changes are actually needed vs. the current GRIB save

  1. Grid: GRIB stores N320 reduced-Gaussian natively; ZarrOutput stores the
  same native cells as a 1-D values dim (542,080) plus latitude/longitude coord
  arrays — lossless, no regridding. Decide native-N320 (compact) vs.
  regrid-to-lat/lon at write (bigger, analysis-friendly). Recommend native +
  regrid on read.
  2. Keep cos_mwd/sin_mwd: the GRIB path was forced to drop these
  (drop_unencodable_wave_dir, the ConceptNoMatchError fix) because they aren't
  GRIB params. Zarr has no such limit — you keep all 120 fields incl. wave 
  direction. Net data gain; remove that drop on the Zarr path.
  3. Add a member dimension. anemoi's stock ZarrOutput writes a flat (time, 
  values) per variable — no ensemble axis. So either (a) a ~30-line subclass
  that region-writes [member_idx] into (member, time, values) arrays (cleanest
  for ensemble stats), or (b) one zarr group per member (member001/…) reusing
  stock ZarrOutput unchanged.
  4. dtype + compression: store f4 (or f2 — the model already runs FP16) and add
  a zarr zstd/blosc codec; GRIB chunks are ~1.6 GB each, compressed Zarr is
  typically smaller.
  5. Chunking: (member=1, time=N, values=full) — one member's slab writes
  cleanly per session (exactly the POC layout).
  6. Commit, don't consolidate: anemoi ZarrOutput.close() calls
  zarr.consolidate_metadata — unnecessary/awkward with Icechunk (it has its own
  manifest). For the Icechunk path you call session.commit() instead.

  Infra / deps
